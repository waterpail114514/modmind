# ModMind 设计规范

适用于 ModMind 软件的功能规划、界面设计、技术选型、工作台 MCP 适配和交付验收。视觉规则依据现有工作台、设置、文件编辑、资源包、测试、构建与发布等界面总结；旧版“物品与装备”页面中的重复大标题、过量说明和层层框架作为反面示例。插件 iframe 界面另有专门规范。

## 1. 产品气质与核心原则

ModMind 是创作工具。界面应像安静、可靠的工作环境：让项目、内容、当前任务和结果成为主角，让界面本身退后。视觉上的精致来自清楚的层级、准确的间距、稳定的对齐和克制的颜色，不来自装饰堆叠。

1. **先让人做事。** 用户进入页面后，应立即看见当前对象、可做的下一步以及操作结果。功能介绍不能挤占第一屏的工作空间。
2. **一个位置只回答一个问题。** 侧栏回答“去哪里”，页面顶部回答“正在处理什么”，内容区回答“具体内容是什么”，就近操作回答“对这项内容能做什么”。同一信息不要在这些位置反复出现。
3. **以任务而非实现组织界面。** 名称、顺序和分组按用户目标组织。API、桥接、缓存、模型线路、构建机制等实现细节只在确实影响选择时出现。
4. **默认简单，深度可达。** 常用操作直接可见；少用操作收进菜单、详情或专业模式，但不能让常用任务先经过高级设置。
5. **状态明确且不打断。** 加载、保存、失败、空内容和不可用状态都应有可理解的反馈；尽量在操作发生的位置反馈，只有高风险或需要决策时使用对话框。
6. **跨页面一致。** 相同动作使用相同名称、图标、位置倾向和状态反馈。用户不应每换一个页面就重新学习一次界面。
7. **离线优先，按体积取舍。** 本地项目已有内容的查看、编辑和保存不应因为断网失效。小型静态参照数据优先内置；大型资源、完整游戏运行时和在线服务不作无条件离线承诺。缺少网络时要明确说明哪些补充内容暂不可用，但不能连带阻断本地工作。

## 2. 页面结构与信息层级

桌面主窗口保持“窗口栏、侧边导航、主工作区”的稳定骨架。侧栏承载跨功能导航，并标示当前位置；不要在普通页面里再搭一套与侧栏竞争的完整导航。主工作区可按任务采用列表/详情、编辑器/预览、表单/结果等布局，优先让内容占据空间。

页面顶部使用紧凑工具栏。需要可见标题时，只显示**一个**能够定位当前任务的标题；已有清楚的侧栏选中项、标签或文件路径时，可以把页面标题保留给无障碍语义，在视觉上只显示必要的上下文。列表区、详情区和弹窗可以有自己的局部标题，但不能把页面名再放大重复一次。标题不是装饰，也不能为了填满空白而增加。

层级建议为：当前对象或任务名称 > 当前状态与关键数据 > 可执行操作 > 次要上下文。版本号、路径、数量等只有在帮助辨认对象或影响操作时才出现。页面不需要“眉题 + 大标题 + 副标题 + 卡片标题”这样的连续重复结构。

内容以行、分隔线、分组标题和适度留白组织。卡片用于可独立选择或比较的重复对象、模态内容、真正需要边框的工具；不要把整个页面切成一层套一层的卡片，也不要用大面积空白制造虚假的高级感。密度应适合桌面创作软件的持续使用，能扫描、能比较、能连续操作。

## 3. 操作层级与放置规则

| 操作类型 | 优先位置 | 表现方式 | 典型例子 |
| --- | --- | --- | --- |
| 当前页面的主要任务 | 页面工具栏右侧，或任务输入/编辑区的自然终点 | 一个醒目的主按钮；执行中显示状态并防止重复提交 | 构建项目、运行测试、导出、发送 |
| 与主要任务紧密相邻的准备动作 | 主按钮左侧或同一工具栏内 | 次级按钮，顺序按工作流排列 | 预检 → 发布、同步 → 启动 |
| 作用于单个对象的动作 | 对象所在行、详情标题栏或编辑器工具栏 | 就近按钮；常用动作可直接显示 | 打开、保存文件、刷新当前列表 |
| 搜索、筛选、排序、视图切换 | 列表或结果区顶部 | 输入框、筛选控件、分段控件或标签 | 搜索模组、切换预览与源码 |
| 低频维护与辅助动作 | 对应区域的“更多”菜单或详情中 | 图标按钮或菜单项，提供名称提示 | 打开目录、复制路径、诊断信息 |
| 批量操作 | 用户选中对象后，紧邻选择范围 | 有选择数量的批量工具栏 | 批量移除、批量导出 |
| 危险或不可逆操作 | 对象附近，但视觉上与主操作分开 | 危险色；明确影响范围，必要时确认 | 删除文件、移除模组 |
| 全局应用操作 | 窗口栏、全局菜单或设置 | 全局一致的入口 | 账号、外观、窗口控制 |

同一操作只保留一个主入口；必要的快捷入口可重复，但其名称和结果必须一致。一个操作区通常只有一个视觉上的主按钮。不要让多个同色主按钮互相争夺注意力，也不要把“刷新”“打开目录”之类的辅助动作提升到与“保存”“开始”“发布”同等层级。

按钮文案使用明确动词和对象，如“导入 Mod”“保存文件”“运行测试”；避免“确定”“处理”“立即体验”等无法预判结果的措辞。熟悉的工具动作可用图标按钮，必须有 `title` 或可访问名称；不熟悉、风险较高或含义依赖上下文的动作保留文字。按钮位置随操作对象走，不为了工具栏整齐把所有动作堆到页面右上角。窄窗口时先保住当前主操作，再收纳辅助动作；不要让文字拥挤、截断或互相覆盖。

## 4. 文案与标题

界面文案短、具体、面向结果。字段标签说明要输入什么；按钮说明会发生什么；状态说明已经发生什么、接下来能做什么。空状态可用一句话交代当前状况，再给出最相关的行动。错误先说明用户能理解的影响和恢复路径，技术详情按需查看。

**默认不放小字说明。** 尤其不要在每个标题、字段和按钮下面补一行技术原理、内部流程、营销式解释或重复标签。小字不是解决信息架构不清的补丁，它会降低可扫描性，破坏整页的秩序。只有以下内容可以保留辅助文字：会改变用户决定的限制或后果、输入格式和验证要求、无法从控件本身理解的重要状态，以及法律或安全要求。即使需要说明，也应优先精简标签、改进控件或在恰当时机显示；长篇实现细节放入可展开详情或诊断视图。

标题只为导航和内容分组服务。页面名不要在侧栏、页首、列表头和内容主视觉中连续重复；局部标题要比页面标题明显更轻。不要使用“欢迎来到”“你可以在这里”或“这个功能将帮助你”等空泛句子占据工作区。工作台的空白状态可以有一句有辨识度的引导语，但不能把这种大字欢迎语复制到每个工具页。

## 5. 控件、反馈与工作流

设置项按用户理解的主题分组，标签和控件稳定对齐；二元选项用开关或复选框，互斥模式用分段控件或选项组，多项选择用下拉或菜单。能直接修改并即时生效的设置不额外放“保存”按钮；需要明确提交的表单把保存放在表单末尾或固定操作区，并让未保存状态可见。

编辑场景保留当前对象、返回来源、修改状态和保存结果。切换文件、主题或视图时，尽量保留草稿、选区和滚动位置；若会丢失修改，应在离开前说明并提供选择。运行中应显示阶段或进度，避免只有转圈且不知是否成功。完成后把结果放在原工作流里，优先显示可读摘要，再提供日志或原始数据。

确认框只处理真实的风险、不可逆后果或需要明确选择的冲突。危险按钮和确认文案写明对象与后果，不使用泛泛的“是否确定”。失败后保留用户输入与上下文，提供就近重试；不要只靠会消失的通知承载重要错误。

键盘焦点、禁用原因、窄窗口布局和深浅主题都属于规范的一部分。固定格式的工具栏、图标按钮和列表行应保持稳定尺寸，状态、图标或文案变化不能让布局跳动。正文和控件文字要清晰可读；“小字更精致”不能作为降低字号的理由。

## 6. 视觉语言

以中性表面、清楚的文字、细分隔线和有限的强调色建立层次。ModMind 的青绿用于主要操作和选中状态，金色只作少量细节点缀，不承担正文信息。颜色必须来自共享语义主题变量，浅色、深色和自定义主题下保持可读与一致；具体颜色源和生成方式以 [全局主题文档](theme-system.zh-CN.md) 为准。

空间应服务阅读与操作：相关控件靠近，不相关组用间距或细线分开；不要靠巨大的内边距、装饰性渐变、模糊光斑、悬浮大卡片或过多阴影营造“设计感”。图标只用于提高识别速度，不代替关键动作名称。字体层级少而稳定，页面标题、分组标题、正文、辅助数据各有明确角色；不在小面板里使用展示级大字。

## 7. 明确禁止的模式

- 同一页面名以多个大标题或醒目标签重复出现，尤其是侧栏已选中后在主区再用大标题占位。
- 在字段、按钮或分组下普遍追加灰色小字，解释技术原理、内部实现或显而易见的操作。
- 一屏内堆叠多个主按钮、多个互相竞争的操作栏，或让危险动作紧挨默认主操作。
- 页面大卡片套小卡片、每个信息块都加边框，以及为“高级感”牺牲可用空间。
- 用欢迎页、功能介绍或空泛口号替代可直接使用的工作界面。
- 把日志、JSON、内部路径、版本协议、缓存状态等技术细节当成普通用户的主要内容。
- 用颜色单独表达状态；用禁用按钮代替解释用户为何暂时不能继续。
- 让文本溢出、操作在窄窗口消失、状态变化引起工具栏跳动，或让弹窗遮住必要上下文。

## 8. 功能是否够用、是否好用

AI 评审页面时，不能用按钮数量、字段数量或“已经能增删改查”判断功能充分。先写出目标用户在该页面要完成的主要任务，以及每项任务从**找到对象 → 理解现状 → 操作 → 验证结果 → 继续或恢复**的完整路径。只要路径中的关键一步必须离开页面猜测、手工查资料或反复试错，就不能称为“功能已足够”。

对每项主要任务按下面七项逐项评定：`0` 为缺失，`1` 为能完成但需要明显绕路或猜测，`2` 为在当前上下文顺畅完成。关键任务任何一项为 `0`，页面不能通过功能验收；任何一项为 `1`，必须记录具体阻力与改进方案，不能仅以视觉打磨结案。

| 评定项 | 应检查的问题 |
| --- | --- |
| 任务覆盖 | 用户需要创建、查看、比较、编辑、删除、导入、导出或测试的哪些行为？主要任务是否有完整闭环？ |
| 内容与参照 | 用户要处理的对象是否找得到？已有内容、系统自带内容和项目自制内容是否明确区分？需要参照现有作品时，能否直接查看？ |
| 查找效率 | 对象增多后能否搜索、筛选、排序或按类型缩小范围？能否清楚地回到当前选中对象？ |
| 判断依据 | 做决定前能否看见实际效果、关键属性、限制和影响范围？预览是否真实代表最终结果，并明确尚未覆盖的部分？ |
| 操作效率 | 高频动作是否就近、步骤是否符合工作顺序？能否批量处理确有批量需求的对象，而不必机械重复？ |
| 结果与恢复 | 保存、构建或应用后能否验证生效？错误是否指出可修复的问题？未保存内容、取消、重试和误操作能否妥善处理？ |
| 边界与状态 | 空列表、大列表、加载、离线、只读、不支持和窄窗口下是否仍可理解并继续工作？ |

评审应使用真实任务样本，而非只看静态截图。至少走通首次使用、已有大量内容、失败后重试和从结果返回编辑四种情境。写出具体的任务与阻断点，例如“要比较项目物品与原版铁剑时，必须离开页面查找原版属性和外观”；不要写“功能较少”“体验一般”这样的空泛结论。

还应在**首次启动且完全断网**的条件下重走任务，记录哪些步骤可用、哪些依赖在线资源；不能以“用户曾经联网过、有缓存”作为首次离线可用的证据。本地项目的基础查看、编辑和保存应继续工作。对静态参照目录，先估算覆盖当前支持版本所需的总大小：若原始 UTF-8 数据（含索引和版本差异）**不超过 256 KiB**，优先考虑随应用内置；超过这一体积时不硬性要求全量离线，应评估最小基线、按需获取、用户主动下载或明确降级，并考虑多个功能累加后的安装包大小。256 KiB 是评审阈值，不是允许每个页面无节制增加 256 KiB 的配额。

不得为了让一个目录或预览离线可用，就自动下载数 GB 的 Minecraft 客户端、运行时或整套资源。大体积下载必须由用户为对应任务主动发起，并在开始前说明下载量；没有这些资源时，应保留本地可完成的工作流。当前物品目录的 1.20.1 基线加 1.21.1 差异共约 148 KiB，属于适合内置的小型数据；完整游戏贴图与运行时不适用这一判断。

确需联网的补充能力应标明它获取的内容，并有超时、失败、重试和可取消的状态。网络错误不得伪装成“项目没有内容”；离线时也不能长时间只显示加载动画。可缓存的结果应按项目或游戏版本隔离，避免把旧版本数据当成当前版本的事实。

“物品与装备”页可作为功能评审样例：仅能编辑自制物品、选择贴图和保存，不等于用户已经能判断物品做得对不对。应检查原版物品能否作为**只读参照**被找到，列表能否按名称、ID、来源或类型筛选，选中后能否看见可信的外观与关键属性，保存后能否顺畅进入游戏验证。原版数据缺失或版本不匹配时要如实说明，不得用几个手写样例冒充完整的游戏物品库，也不能把近似贴图称作最终游戏效果。

AI 提议增加功能时，先说明它解决了哪条任务路径上的阻断，再确定最小可用范围、数据来源、状态处理和验收方式。没有对应任务的功能堆叠不加；有明显任务缺口时，也不能以“避免改动过多”为理由判定现有功能足够。

## 9. 新功能优先复用成熟实现

新增能力先检查仓库已有的组件、业务服务、依赖和工具，再到 GitHub 等上游来源查找可用的开源成品。编辑器、模型渲染、文件格式解析、启动器等已有成熟实现的领域，优先集成合适的库、SDK 或工具。不要因为 AI 能写出一个演示，就重新实现一套功能残缺的替代品。

选型以实际任务适配为准，检查功能覆盖、许可证、目标平台与版本、维护和发布记录、接入接口、依赖体积、联网要求及离线成本。星数或项目介绍不能代替验证。实施前简要记录采用的项目与版本、接入方式及已知缺口；没有合适成品时，说明具体不适配之处再自研。简单的界面逻辑、短小转换和局部修复可直接实现，不必为了复用引入更大的系统。

集成应复用成品的核心能力，由 ModMind 提供符合本规范的界面和工作流。版本与来源应可追溯，更新时能回归验证；修改上游代码时记录必要差异。不能把复杂安装和配置全部留给用户，也不能为了一个小功能自动下载整套大型资源。选型验收要包含真实输入、失败情况、性能和打包后的可用性，而不只确认依赖能安装。

## 10. 需要工作台使用的功能同时适配 MCP

设计新功能时先判断：工作台 AI 是否需要查询这些数据、执行这个动作，或验证它产生的结果？若需要，MCP 接入属于该功能的交付范围，不能等界面完成后默认留作未来工作。展开、拖拽、颜色和布局等纯视觉交互不必逐一转换成工具。

优先复用已有 MCP 工具；需要扩展时按用户任务组织接口，不按页面按钮逐个新增。界面与 MCP 应调用同一业务服务，共享校验、项目作用范围和结果语义，避免出现“两套实现、两种行为”。例如物品功能需要 AI 使用时，应能查询与筛选目录、读取当前定义、执行已支持的编辑操作并检查保存结果；预览若用于 AI 判断外观，应返回可供模型读取的图片或资源，而不只是打开一个窗口。

MCP 交付应具备以下条件：

- **能发现、会调用：** 在工作台实际使用的工具目录与调用路由中注册，提供明确的用途、输入 schema、版本支持范围和前置条件。必要时同步工作台的工具说明。
- **操作范围明确：** 声明只读、联网或写入等副作用，沿用现有权限和确认机制；核对项目、会话、文件路径与修改版本，不能绕过界面已有的约束。
- **结果可判断：** 返回结构化状态、变更对象或产物引用和可恢复的错误。区分“已接收请求”“已完成”和“已验证生效”。大结果支持分页或限量，长任务提供进度与状态查询，并在底层允许时支持取消。
- **能验证闭环：** 从工作台使用的 MCP 调用链走通至少一条真实任务路径，回读验证业务结果，并检查失败、只读限制及项目切换等相关边界。业务函数单测、工具名称出现在列表中或界面按钮可用，都不能单独证明 MCP 适配完成。

交付说明应写清工作台当前能做哪些操作、哪些只支持界面、哪些受版本或资源条件限制。有明确工作台需求而未接通 MCP 时，应标记该部分未完成。

## 11. 新页面验收问题

设计评审至少回答以下问题：用户第一眼能否确定当前对象和最重要的下一步？主要任务是否能从找到对象走到验证结果？对象增多后是否仍能查找与筛选？主操作是否放在任务发生的位置且只有一个视觉主次？删掉所有辅助小字后，页面是否仍然能用？页面名是否只出现一次？次要和危险动作是否按频率与风险安放？空、忙、成功、失败和未保存状态是否都能继续工作？窄窗口、键盘、深浅主题下是否仍然清晰？

若任何问题的答案是否定的，先调整信息架构与操作位置，再考虑增加说明文字或视觉装饰。

新功能还应回答：是否评估了已有能力和成熟开源实现？选型理由与依赖成本是否明确？工作台需要的能力是否已通过 MCP 实际调用并验证结果？
