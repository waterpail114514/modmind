# 创作体验改进开发计划

## 范围

从 2026-09-15 的插件用户记录提炼客户端通用问题。第一批修复共享会话和工具基础，覆盖模组、整合包、服务端插件；不修改用户项目玩法、不改模型服务、不发布安装包。详细证据见 `native-context-recovery-investigation-2026-09-15.zh-CN.md` 与 `server-plugin-creation-feedback-review-2026-09-15.zh-CN.md`。

## 第一批：先止损（本次实施）

| 编号 | 交付 | 验收 |
| --- | --- | --- |
| A1 | 正常续接发送当前请求；只有缺少原生历史时使用备用上下文 | 已知 thread、磁盘恢复、原生分支、故障后新建均有测试；备用提示不谎称一定发生过故障 |
| A2 | 原生 turn 创建时保存位置，区分首次与末次重试 | 中断/空回答仍保存；编辑前使用首次 turn，保留结果使用末次；不得套用其他 thread 的旧位置 |
| A3 | 相同模型、推理强度和 Fast 设置不打断任务 | 无变化保存不产生新配置 revision，真实变更正常生效 |
| A4 | 普通请求错误不等同于会话损坏 | 泛化 invalid request 保留原会话；明确 missing history 仍能查找 rollout 后恢复 |
| A5 | 统一项目上下文来源，修复 Paper 被标为网易 | Paper/Spigot/Folia/Velocity、Java Mod、整合包、Bedrock、网易分别检查 |
| A6 | 原始请求独立归档，日志不再不断追加到需求文档 | 首次普通需求可初始化；已有需求不被自动覆盖；原始反馈完整保留，按 hash 去重 |
| A7 | 默认项目检索限定源码/配置，返回有上限的相关片段 | 排除工具数据、快照、构建、二进制；提供托管检索入口和明确规则，不改用户全局搜索设置 |

兼容策略：旧会话索引继续可读；没有首次 turn 信息的旧轮次不能凭空猜测中断边界。所有归档只保存在当前项目工具目录，不上传用户素材。搜索过滤不影响构建、导出或用户显式读取诊断文件。

第一批验证：纯函数、实际会话存储、模拟 App Server 协议端到端测试；TypeScript 检查与构建。测试不调用付费模型、不操作用户服务器。完成后在本文补充结果和限制。

### 第一批完成记录

2026-09-15 已完成 A1–A7 的客户端实现：

- `externalAgents.ts` 在读取原生会话指针后才选择备用历史；原生 fork 同样保留当前请求。普通 API 请求错误不会触发会话重建，相关提示改为保留原会话。
- App Server 的 `turn/start` 回执和 `turn/started` 通知会及时持久化并去重。`ConversationStore` 新增兼容的 `nativeTurnStarts`，原 `nativeTurns` 保存末次尝试；新 thread 不沿用旧索引，原生分支保留所继承轮次。
- `saveBeginnerAiPreferences` 对完整有效设置比较，无变化直接返回。
- 外部 Agent 上下文统一生成，服务端插件、整合包与 Java Mod 分开描述。
- `captureCreationRequest` 按内容 hash 保存原始反馈；已有需求文件不再自动追加或覆盖，避免损坏用户维护的文档。已积累的旧日志没有自动清除。
- 新增 `modmind_project_search`：只做文字查询，返回路径、行号和有限片段；最多 100 条结果、单文件 1 MiB、扫描文本总计 16 MiB。与项目文件列表共享排除规则；工作台提示优先使用它。

验证：8 个相关测试文件共 185 项通过，1 项原有真实 CLI 测试跳过；`npm run typecheck` 与 `npm run build` 通过。构建仍有模块拆包/较大 chunk 提示。未执行付费模型回放、游戏实测或安装包发布。

边界：提前持久化轮次针对当前托管 Codex App Server 路径，旧 CLI/Claude 没有伪造其未提供的 turn 事件；历史工程缺失的索引不自动推测修补。托管检索有实际过滤，原生 shell 的显式目录搜索由工作台规则引导，不修改用户的全局 rg 配置。原始日志本轮只完整归档，首次发送的日志摘要、旧需求整理及恢复包压缩均为第二批。

## 第二批：让反馈和修复形成闭环（原始设计，实际交付见完成记录）

按依赖顺序交付，不先堆大型界面：

1. **日志反馈卡**：原文引用 + 代表性完整异常链 + 次数/时间 + 用户观察；模型先读摘要，按需读原文。保留独立异常，不能简单裁最后若干行。
2. **当前要求与变更**：每条要求绑定来源消息，明确保留/取消/替代；区分体验目标与实现建议。先只在工作台提供轻量查看和纠正入口。
3. **测试版本和证据**：连接现有构建、快照与运行记录，标出修改、编译、启动、玩法、用户确认各自状态；反馈绑定所测产物，未知则标未知。
4. **重复失败处理**：完成后“还是不行”创建新失败记录；携带上次假设、改动、版本及新观察；执行中“继续”保持续接。不要仅按文本重复决定含义。
5. **结构化恢复包**：根据以上事实生成当前任务包，不再粗暴截取长聊天尾部；原始历史仍可查询，未完成操作的结果保留。
6. **skill 更新**：先更新共用执行规则、插件开发和故障修复；设计、联动诊断、库存交互验收拆成按需 references。模组与整合包使用各自验收对象。
7. **效果评估**：按任务比较 token 输入/缓存/输出、首次可测试产物耗时、重复失败轮数、最终结果。恢复成功不计作玩法成功。

第二批验收样本：重复异常 64 次但保留另一个独立错误；先禁止替身后明确允许；“已构建”不能自动变成“实测通过”；同一句失败反馈关联不同产物；原生恢复失效后仍保留最新约束。全部采用脱敏缩小样本。

### 第二批拆分交付

| 子批次 | 具体交付 | 依赖与验收 |
| --- | --- | --- |
| B1 日志与反馈 | 在第一批原始归档上增加异常聚类、代表堆栈、次数、触发动作和原文范围引用；工作台可展开原文 | 可独立上线。混合日志不能漏掉独立异常，模型收到摘要而非重复全文 |
| B2 要求与版本 | 当前有效要求及来源/替代关系；把已有产物、配置与验证结果绑定同一版本 | 用户可纠正归纳；未知测试版本不猜测；插件/模组/整合包各自展示合适的验证阶段 |
| B3 失败与恢复 | 交付后重复反馈建立新失败；关联 B1/B2；生成结构化恢复包；恢复原因用结构化事件保存 | 正常续接继续使用增量；重建保留最新条件和未完成工作，不丢用户原文 |
| B4 skill 与评估 | 更新共用规则和插件/修复 skill，按需加载设计、联动诊断、库存验收参考；固定脱敏回放样本 | 不强制每轮跑全套检查；比较耗时、用量、反馈轮数和完成质量，不承诺固定省钱百分比 |

建议先交付 B1，再交付 B2；B3 使用前两者的数据，B4 随每个子批次补齐规则与回归。根据后续讨论，第二批同时加入下述玩家测试能力；复杂视频编辑、配置编辑器和自动模型路由仍留到第三批。

### 第二批补充：升级 MCP，接入玩家测试

目标：AI 能在本机隔离服中让测试角色实际触发功能，并拿到本轮客户端/服务端日志与状态。需要视觉验收时使用真实客户端渲染。复用现有进程管理、下载、HeadlessMC、服务端场景、证据归档与 ModMind MCP，不另建一套绕过托管生命周期的服务。

#### 已检索的现成方案（2026-09-15，文档级调查，未安装实测）

| 方案 | 文档确认的能力 | 接入判断 |
| --- | --- | --- |
| yuniko-software/minecraft-mcp-server | 基于 Mineflayer，暴露移动、视角、物品、方块、聊天等 MCP 工具 | 可作为协议机器人候选；README 当前强调 1.21.11，不能据此保证 1.20.1 或模组协议兼容 |
| Mineflayer | 现成机器人基础；npm latest 4.39.0 要求 Node >=22 | ModMind Electron 33 使用 Node 20，需选兼容依赖或托管独立进程，不能直接无版本约束安装 latest |
| prismarine-viewer | 机器人世界的网页渲染，提供 headless 视频输出 | 可辅助观察位置和世界，不能当作 Minecraft 原生渲染、原版 GUI 或复杂 Mod 画面的验收证据 |
| HeadlessMC + hmc-specifics | 真实客户端内的 gui、click、text、聊天命令、背包/tooltip、key；文档示例 key f2 截图 | 与现有基础最接近。功能按版本/Loader 探测；README 与网站的 1.20.1 支持表不一致，需核实发布资产 |

HeadlessMC `-lwjgl` 会将 LWJGL 调用改为空实现；`hmc-optimizations` 也可能跳过渲染。此模式能读结构化 GUI/运行逻辑，不提供有效的原生画面验收。需要真实截图时启用完整资源和渲染路径，不使用 dummy assets；隐藏窗口仍需保持渲染。官方提到 Linux 可用 Xvfb，但不能把此结论直接套到 Windows。Windows 隐藏、失焦和最小化后的渲染/输入行为必须实测；不满足时明确请求可见客户端，而非返回黑图并声称通过。

#### 完整实施顺序（合并日志和客户端测试）

| 顺序 | 交付 | 完成条件 |
| --- | --- | --- |
| 1 能力验证小样 | 对 Paper 1.20.1 核实匹配的 hmc-specifics 发布包；验证持久在线、进服、玩家命令、菜单读取/点击，以及 Windows 有渲染但不抢焦点的截图路径。协议机器人作为独立候选比较 | 输出可复现结果与不支持项；不先承诺全版本或无窗口截图 |
| 2 统一测试会话 MCP | 准备/启动/状态/停止，绑定项目、运行 ID、角色身份、产物和依赖；服务端与客户端统一取消和清理 | 插件部署在服务端；客户端使用独立测试配置。旧会话不能误操作新实例，重试不重复启动角色 |
| 3 日志反馈 B1 + 版本证据 B2 | 自动接入构建、服务端、客户端日志，同时支持用户粘贴；按游标返回新增信息，保存完整原文与关键异常 | 不混淆实际服和测试服；命令发送、结果返回、预期通过分开；匹配成功文字也不能忽略新异常 |
| 4 玩家动作 MCP | 发送玩家命令、读取玩家/菜单/背包信息、点击槽位、有限时长按键；管理员权限由托管测试服设置并恢复 | 实际走玩家事件，准备库存不算库存交互验证；普通玩家与管理员分别验收。动作结果要有新证据，未知状态禁止盲重试 |
| 5 最小画面证据 | 支持的真实渲染客户端按需截图或短帧序列，标注视角、时间和角色；有必要才启动第二观察者 | 无头空画面、非原生 viewer 不能冒充原版视觉。先验证本案翻滚、倾斜、跟随与退出清理 |
| 6 当前要求、失败和恢复 B2/B3 | 记录当前条件、已认可效果、上一轮假设；重复失败关联所测版本；按需生成恢复包 | “还是不行”成为新反馈；正常续接不回灌历史；没有游戏实测就不自动判玩法通过 |
| 7 skill 和评估 B4 | 根据工具真实能力选择无头逻辑/真实画面/人工确认路径；补插件、模组、整合包的最小验收；固定脱敏回归样例 | 至少覆盖进服、玩家命令、权限、库存消耗、失败清理、中断恢复和一个视觉场景；统计消耗及返工轮数 |

MCP 接口先以少量操作分类实现（名称为设计草案）：`modmind_test_session` 管会话与角色，`modmind_test_observe` 读状态/GUI/新增日志，`modmind_test_action` 做玩家动作，`modmind_test_capture` 取真实画面，`modmind_test_scenario` 执行有断言的短场景。返回 `sessionId`、步骤、状态、证据引用与未验证项；槽位点击关联最近观测版本，过期就重新读取。

减少消耗：优先结构化状态而非每步截图；等待状态变化而非让 AI 每 tick 轮询；确定步骤合成短场景，执行器完成后返回证据；失败返回相关新增异常，不重复全量启动日志。测试账号只作用于托管隔离实例；管理员权限恢复为测试前状态，不改正式服。

以上为原始验收目标。实际实现及验证边界以下面的完成记录为准，不将候选版本目录视为游戏实测。

## 第二批完成记录与未通过项（2026-09-15）

### 下载链路与镜像决定

不建设自有镜像，不内置全版本 JAR。内置的是小型能力目录，运行时按游戏版本与 Loader 精确选择文件；工具 JAR 使用固定 SHA256，损坏缓存重下，共享用户目录缓存。同一文件不会因每个项目都重新下载。

| 资源 | 代码配置的来源 | 覆盖和限制 |
| --- | --- | --- |
| Minecraft 版本元数据、本体与资源 | https://bmclapi2.bangbang93.com 与 Mojang 官方 | 优先复用现有运行时管理器；HMC 的缺失依赖回退仍可能直连官方，不能承诺全链路只走镜像 |
| JDK | https://mirrors.tuna.tsinghua.edu.cn/Adoptium/、https://mirrors.ustc.edu.cn/adoptium/releases/、Adoptium 官方 | 具体系统/架构/版本逐个判断；Adoptium 元数据查询仍依赖其 API |
| Gradle | https://mirrors.huaweicloud.com/gradle/、https://mirrors.cloud.tencent.com/gradle/、https://services.gradle.org/distributions/ | 按用户来源偏好；不保证镜像永久保存全部版本 |
| HeadlessMC / Specifics | GitHub 作者发布页；https://ghfast.top/ 加速后备 | ghfast 是第三方 GitHub 加速，不是独立维护的完整资源镜像，不作长期可用承诺 |
| 模组与整合包内容 | 各发布平台、作者来源 | 没有覆盖一切的合法稳定通用镜像；需要遵守来源分发限制和平台下载流程 |

未来只有实际失败率表明值得维护时，才讨论托管小体积、固定版本的测试组件镜像。不要为了少量小众组件维护所有 Minecraft、JDK、模组、整合包资源。镜像不会使不兼容的控制组件变成兼容。

### 实际验证

- 最终 10 个相关测试文件共 171 项通过，1 项原有真实 CLI 测试跳过；覆盖原生会话选择/恢复、中断保存、偏好无变化、需求替代、64 次重复异常及独立异常、过期 GUI 操作、输入通道 EPIPE、权限恢复/取消队列、MCP 只读边界、成功文字混合新异常。
- TypeScript 与生产构建通过；5 个修改的 skill 均通过 quick_validate（Windows 按 UTF-8 读取）；构建保留原有拆包/大 chunk 提示。
- 隔离 Electron 最终冒烟通过：没有新增反馈面板、没有新增页面接口、首次附件仍自动摘要。可复现脚本 `scripts/creation-feedback-smoke.mjs`；结果 `test-results/creation-feedback-live/1789484324857/report.json`。早期带面板的截图仅为开发记录，已经撤回，不是交付界面。
- 真实 1.20.1/Fabric 0.19.3 + Specifics 1.2.2 在隔离临时目录启动，读到了 Minecraft 原生辅助功能欢迎页、按钮、文字，返回 gui/click/text/menu/close/msg/connect，inventory/tooltip/key 为 false。
- 初次实测遇到错误 Java 版本、测试缓存中损坏的 intermediary JAR；修正隔离测试环境后启动通过。EPIPE 未捕获问题已在客户端适配层修复并加回归。
- 本机独立原版 1.20.1 测试服启动遭遇 Java NIO 回环连接 `Invalid argument: connect`，没有监听端口；客户端 connect 返回“正在连接”，随后失败，玩家命令返回“需要进入游戏”。未把发出连接当作进服成功；本轮未修改服务端来绕过此环境问题。
- 因此第二批反馈/恢复基础已交付，玩家测试接口已实现但端到端游戏验收未完成。不得将这一状态改写为“第二批全部游戏功能通过”。

## 第三批完整规划：减少返工，减少下载和模型消耗

以下为下一阶段计划，不是已实现功能。先补测试链路的实际验证，再做复用和可视编辑。保持现有聊天页布局，优先复用快照、附件、资源编辑器、运行时管理器。

### 实施顺序与验收

| 顺序 | 工作 | 对用户的直接作用 | 依赖／验收 | 适用 |
| --- | --- | --- | --- | --- |
| C0 | 完成真实游戏验证基线 | AI 说“测过”时有可核对的实际证据 | 在能启动隔离服的 Windows 环境跑 1.20.1 进服、命令、op/deop、断线清理；再跑一个现代版本的背包/按键/截图；全部记 exact 版本与失败点 | 插件、整合包；模组通过测试包 |

建议拆成三个可独立交付的小阶段：

1. **第三批 A：可靠性和省消耗。** C0、C1、C3、C4、C9 基础统计。先解决“测没测、版本对不对、重复读取多少”。C0 未通过不宣传全自动验收。
2. **第三批 B：复用测试和视觉反馈。** C2、C5，配合 C7 的一个现代版本。优先复测日志中暴露的库存消耗、权限、重登清理和视觉跟随问题；每种场景都保留失败样本。
3. **第三批 C：模式编辑能力与覆盖面。** C6、其余 C7。C8 为独立探索，不阻塞通用能力。镜像托管只在 C3 的实测数据支持、且用户重新授权后单独规划。

### Skills 怎么做

| Skill / reference | 增补内容 | 什么时候读，避免增加消耗 |
| --- | --- | --- |
| minecraft-build-repair | 失败证据 → 可区分的假设 → 最小修改 → 对应复测；重复失败时检查版本和前置条件 | 构建/运行失败或用户反馈未解决时；不每轮重复读全部参考 |
| headless-minecraft-testing | 经过实测的能力目录、场景复用、普通/管理员身份、库存证据、无法自动验收时的短人工步骤 | 实際玩家测试；先查询能力再下载，不先猜工具版本 |
| minecraft-server-plugin-development | 本服 API/事件链、权限、目标匹配、消耗写回、视觉观察者、退出清理 | 对应行为修改时读细分 reference，不把案例需求当通用规则 |
| minecraft-mod-development | 开发客户端与正式包差异、GameTest/独立服务端选择、自定义 GUI/网络、资源视觉验收 | 与变更相关的路径；不要求所有 Mod 都跑所有测试 |
| minecraft-modpack-authoring | 客户端专属依赖、配置覆盖、脚本、任务与资源包；冷启动/新世界/重登的选择 | 联动或整合包变更时；启动通过不代表全部内容通过 |
| 共用执行规则 | 成功版本保护、版本不明先核对、查缓存、按需读原文、不能将助手结论当认可 | 共用规则保持短；具体流程放 reference，优先让代码保证不变量 |

不为每个痛点新建一个 skill。先扩展已有 skill 的按需参考；只有独立入口能明确减少误路由时才新建。新增编辑器不是 skill 的替代品，skill 也不能代替确定性的状态校验。

### 验收样本和发布门槛

使用脱敏的小工程：64 次相同异常夹独立错误、先禁止后允许的要求、同一句失败反馈对应不同构建、会话中断后有未完成操作、过期 GUI、操作成功文字后出现异常、截图为空或来自旧版本、已下载 hash 错误、取消时临时管理员还原。每个样本检查原始证据可追溯、没有静默丢条件、没有把未知变成通过。

每个子批次交付代码、相应回归、实测矩阵和已知限制；不跑付费模型基准就不报告费用下降比例。不自动改模型、不默认增加多 Agent、不建设大型镜像、不内置全版本测试 JAR。新的 UI 只进入已经存在且语义合适的页面，并先给可审查效果，聊天首页不增加记录表单。
