实现选用了渲染线程的 OpenGL 读取，以及 26.3 SDL/Minecraft GPU 截图路径；没有引入 Windows Graphics Capture 或桌面图像依赖。当前验证平台是 Windows x64。人工持续打字、物品取放语义、跨 DPI/全屏及窗口重建、最小化/隐藏/锁屏等原始验收目标仍未被本轮证明，不计为已通过；已验证窗口缩放、原始鼠标关闭与 Vulkan 专项。源码和构建已就绪，未发布或覆盖用户已安装的软件。

以下保留 2026-10-29 的原始方案、候选调研与验收目标，用于追溯设计；其中的计划时态、候选方案和早期状态不代表当前交付。当前实现、精确计数、测试替代项和边界均以上述最终记录为准。

## 1. 确定需求

目标是：**AI 能看见真实游戏画面，并在游戏不占前台、不占用用户键鼠的情况下直接操作。全版本指 ModMind 当前已支持的全部 Java 游戏版本及 Loader 组合，不额外扩展旧 Alpha/Beta、周快照或软件尚未覆盖的版本。**

范围以仓库内置与联网项目目录的并集为准，包含 ModMind 已列出的实验性目标。当前静态调查为 **63 个 Java 游戏版本、133 个模组 Loader 组合**，逐项结果与证据见 [适配调查](game-control-compatibility/README.md) 和 [逐组合矩阵](game-control-compatibility/loader-combinations.md)。不同版本共用操作协议，实际能力基于输入/渲染后端探测，不能仅因不在第三方控制包目录中就禁用操作。后台桥计划在受管测试 JVM 启动时通过 Java Agent 加载；进程内适配仍需要自己的源码、构建和验证记录。

核心循环是：

```mermaid
flowchart LR
  G[后台游戏进程] --> C[真实画面捕获]
  C --> AI[AI 看图决定动作]
  AI --> I[进程内虚拟键鼠]
  I --> G
```

本次交付范围包括截图、鼠标移动/点击/拖动/滚轮、按键/组合键/持续按键、文字输入、执行后重新截图，以及停止和用户接管。控件树、背包数据、世界状态、语义断言、寻路、测试夹具和游戏内 Mod 都不作为这两项能力的前置条件。

“全版本”的实现方式是让控制层与游戏版本解耦。各版本本身的安装、Java、Loader 和启动兼容性仍由已有运行时负责；不能把“同一控制通道可操作已运行窗口”写成“所有历史版本均已完成启动实测”。

## 2. 技术路线

前一版的“系统捕获 + SendInput”只能作为前台控制候选，不能满足后台操作。此次将主路线修正为 **启动时 Java Agent + 进程内虚拟输入 + 后台真实画面捕获 + 现有 MCP**。这是一条待游戏实测的工程方案，API 和源码调查不能单独证明全版本兼容。

AI 仍通过画面识别菜单、按钮和世界，发出按键、鼠标、文字等动作。桥接组件让这些动作进入游戏的输入处理链，继续触发游戏和 Mod 的正常交互逻辑，不直接改库存或调用按钮业务函数代替点击。

具体分工：

- 启动：在 ModMind 自己启动的测试 JVM 中用 `-javaagent` 加载桥。使用标准 [Java Instrumentation](https://docs.oracle.com/en/java/javase/21/docs/api/java.instrument/java/lang/instrument/package-summary.html) 在类加载时接入输入库，避免每个 MC/Loader 都等待外部控制 Mod 的发布包。
- 虚拟设备：每个游戏会话独立维护按键状态、鼠标按钮、位置、相对位移、滚轮和字符事件。AI 动作只写这套状态，不发送到用户桌面的系统输入流。
- 输入接入：旧 LWJGL 路线适配 Keyboard/Mouse 的事件队列和状态轮询；现代 LWJGL/GLFW 路线适配已注册的键盘、字符、鼠标、滚轮回调以及相关查询。两者都必须同时覆盖事件和持续按住状态，动作在游戏输入线程的合适位置派发。
- 后台焦点：只对当前测试窗口的游戏侧焦点查询与回调做受控处理，保持游戏继续接收虚拟输入；实际操作系统焦点仍属于用户当前应用。同时处理失焦清键、自动暂停、锁定/重定位真实鼠标等路径，不能只伪造一个 focused 返回值。
- 真实画面：窗口仍渲染时，优先比较 Windows.Graphics.Capture 与已有 Electron desktopCapturer；需要更直接的 OpenGL 图像路径时，在渲染线程最终画面提交前捕获实际显示帧。不能随便读取某个 FBO 作为最终画面，必须保留正确图形状态并识别实际渲染后端。
- 会话及结果：复用已有项目、PID、取消、清理、图像编码及证据存储。桥的通信使用会话凭据，仅允许受管实例；截图通过现有 MCP 图片内容返回给模型。

Windows 的 [CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow) 可按窗口句柄创建捕获对象，最低系统要求为 Windows 10 1903。后台输入不使用 SendInput；PostMessage 也不能统一替代事件回调、状态轮询和 Raw Input。

适配优先围绕输入/渲染库家族，降低每个 MC 版本的维护成本。范围内的 LWJGL 分支、方法签名、Loader 类加载器、模组直接原生调用和替代渲染器仍可能需要专门适配。只写两套适配器不构成“已支持版本全部覆盖”的证据；全部现有组合仍须逐项验收。

后台运行的基础验收是用户在别的窗口正常工作时游戏持续可控；遮挡、最小化、隐藏和锁屏分别验收。最小化可能停止渲染或出现零尺寸 framebuffer，输入桥本身不能解决；需保持有效渲染表面和出帧路径，或采用独立图形运行环境，不能返回旧帧。Windows 虚拟桌面或 CreateDesktop 也不能直接提供一套独立系统键鼠输入桌面，参见 [Windows 桌面机制](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops)。

如果要求完全不改变游戏进程，同时用户继续使用主机键鼠，可以评估独立虚拟机/图形会话，让游戏在该环境内部拥有前台，再传回画面和动作。其内存、GPU、系统资源与安装成本更高，只有实际评估后才能采用。macOS/Linux 亦需独立验证运行时、捕获和图形行为。

## 3. 已有能力与开源参考

本轮已检查仓库：游戏运行时可以返回受管进程 PID；现有真实交互路径依赖 Minecraft Mod MCP / HeadlessMC；尚未发现可直接复用的后台虚拟输入桥。已有 Java 截图助手可作帧捕获参考，但不能证明后台出帧。

| 来源 | 采用或借鉴内容 | 依赖与适用边界 |
| --- | --- | --- |
| 仓库 MinecraftRuntimeManager、受管进程和测试会话 | 启动、PID、项目边界、取消、停止及退出清理 | 直接复用，控制层不重做启动器 |
| [Electron desktopCapturer](https://www.electronjs.org/docs/latest/api/desktop-capturer)（现有 Electron 依赖，MIT） | 窗口源与画面流候选 | 不增加另一套浏览器；原生游戏画面、精确窗口绑定及新帧行为需验证 |
| [Win32CaptureSample](https://github.com/robmikh/Win32CaptureSample)（MIT） | Win32 窗口捕获、帧池和尺寸变化的成熟示例 | 审核源码并固定提交后复用必要部分；不将示例应用整包交给用户运行 |
| [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) | 系统提供的真实画面捕获 | 使用系统 API，不实现渲染器；游戏/驱动的实际表现需验收 |
| [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) | 前台控制候选 | 注入共享系统输入流，不能承担本方案的后台独立键鼠 |
| [ASM](https://asm.ow2.io/)（BSD-3-Clause） | 加载时修改少量输入库方法 | 优先评估的轻量字节码工具；固定版本、隔离命名空间，核对宿主 Java 和目标 class 格式；不自写字节码解析器 |
| [Byte Buddy](https://github.com/raphw/byte-buddy)（Apache-2.0，含 BSD ASM） | 成熟 Agent 构建与转换接口 | 高层候选；支持的 Java 范围随具体发行包不同，包体通常高于直接使用 ASM，实施小样测量后确定 |
| [ProtoInput](https://github.com/Ilyaki/ProtoInput)（MIT） | 进程内输入重定向、焦点与光标处理经验 | Windows 原生 Hook 候选；有额外 DLL/架构及依赖成本，与 JVM 输入桥先做适配性比较，不能假设可直接覆盖 Minecraft 全版本；不启用会锁住用户桌面输入的行为 |
| Playwright 等视觉自动化的通用工作流 | 看图、有限动作、等待、再观察及失败截图 | 借鉴交互方式；游戏不依赖浏览器或 DOM |

自研的是符合 ModMind 生命周期与 MCP 的后台桥、虚拟设备、输入适配和画面管理。字节码转换、窗口捕获和编码优先复用成熟实现。实施前记录采用库/示例的提交、实际许可、编译环境、Agent/helper 体积及离线依赖；现有 Node 的 @xmcl/asm 不能代替 JVM 内的 Java 字节码库。

原有 Minecraft Mod MCP / HeadlessMC 可继续承担已有专项能力，其版本目录不再决定基础看图与键鼠控制是否开放。

## 4. 业务接口

沿用现有工具，避免让 AI 再学习一套平行入口：

| 工具 | 基础画面控制模式 |
| --- | --- |
| modmind_test_session | 启动受管游戏与 Agent、查询状态、暂停、恢复、停止；分别返回后台输入、捕获及继续渲染的实际能力 |
| modmind_test_capture | 获取目标窗口的新画面，返回图片、frameId、时间、画面尺寸和坐标版本 |
| modmind_test_action | 点击、双击、移动、相对移动、按下/释放、组合键、拖拽、滚轮和输入文字；可请求动作后截图 |
| modmind_test_observe | 查询窗口、焦点、执行结果及已有日志；不强行要求返回游戏内部状态 |

动作都绑定当前项目与 sessionId；坐标动作同时绑定最近画面的坐标版本，窗口尺寸/DPI 改变后重新截图。工具 schema、插件发现、宿主校验和权限路由同步更新，界面与 MCP 共用服务。

建议提供一个可选的短动作批次，以完成“按住 W 并移动鼠标，持续一小段时间，再释放并截图”。批次有总时长和动作数上限，执行期间仍能取消；不能让模型逐帧调用工具维持按键。

MCP 必须把实际图片内容交给有视觉能力的模型，不能只返回本地路径。界面实时预览和模型观察分开：预览可以连续更新，模型按需取新帧，不默认向模型发送完整视频流。

## 5. 必须处理的实际细节

**坐标与视角。** 区分截图像素、虚拟光标、窗口客户区及 framebuffer；菜单操作使用游戏侧坐标，视角操作使用虚拟相对位移。窗口移动或跨屏后更新转换。相对位移不承诺直接等于某个转向角度，AI 以新画面判断结果；后台操作不得移动、隐藏或锁住用户真实光标。

**焦点与用户接管。** 后台控制期间操作系统焦点保持在用户所用应用，游戏输入桥只消费虚拟设备，过滤会干扰它的物理设备事件；不能反复激活游戏来伪装后台。用户切换普通应用不暂停 AI，主动接管游戏时才交接输入所有权并释放虚拟按键。桥失效应暂停并返回具体原因，不能静默退回共享系统键鼠。

**文字。** 普通按键与字符事件分别处理；在游戏输入链注入字符，验证 ASCII、中文、组合键和版本原生输入限制。不借用户当前前台输入法或剪贴板完成后台输入，也不承诺虚拟字符事件等同完整 IME 交互。

**真实新帧。** 动作后请求晚于动作派发的新帧，并标注时间；只能证明取得了后续画面，画面上的结果由 AI 判断。窗口重建、帧池尺寸变化、切屏、失焦、最小化和帧停止更新都要检测。后台被遮挡时必须取得持续更新的游戏内容；零尺寸/停帧时返回不可用并恢复有效渲染条件，不能自动抢前台。

**重复与清理。** 动作 requestId 去重，超时先查询执行结果，避免重复点击或丢物品。虚拟按下状态有最长时限；取消、桥失联、进程退出和项目切换释放自身按住状态，清理自己的捕获会话。超时恢复逻辑不能依赖 MCP 下一次调用才能释放按键。

**权限和资源。** 复用已有真实界面测试开关、读写权限及项目范围。只在 ModMind 启动的受管实例内加载已校验 Agent；这不限制 MC 版本。设置图片大小、帧缓存、动作时长和证据容量上限，桥随功能包交付，不要求用户安装开发工具或下载各版本控制 Mod。Agent 需要处理 Loader 自定义类加载、不同 Java 运行时和依赖冲突，不能假设 premain 成功就代表输入已经接通。

## 6. 实施顺序

按能力交付，不按 Minecraft 版本开放：

1. **后台可行性小样**：用旧版 LWJGL 与现代 GLFW 两类真实客户端，验证用户持续在前台文本窗口打字时，游戏能够在后台移动、转向、操作菜单并持续返回新图。记录类加载、焦点、光标与渲染问题；这些是阻断是否解除的证据，不是仅展示 Agent 已加载。
2. **完整键鼠**：持续/组合按键、相对鼠标、拖动、滚轮、字符事件、短动作批次，以及虚拟焦点、用户接管、暂停和停止。
3. **接入与打包**：沿用现有测试入口和 MCP 权限链，交付 helper、诊断、截图回读及离线本地控制；没有游戏资源时仍沿用已有运行时反馈。
4. **兼容性验收**：按输入/渲染路径选择历史与现代版本验证同一控制通道，修复系统捕获及输入问题。样本不是功能白名单，新增版本无需先制作适配 Mod 才能使用。

公共实现可用旧 LWJGL2 与现代 LWJGL3、不同 Loader、自绘 GUI 和常见渲染 Mod 调通；最终验收按已生成矩阵中的全部 133 个组合逐项完成。当前范围为 1.6.4 至 26.2 中实际列入目录的 63 个版本，不将这个区间误写成区间内所有发行版都受支持。目录变化时重新生成矩阵。另列 79 个服务端插件目标及代理/非 Java 创作目标的边界，不能将它们与 Java 模组组合或已验证后台能力混为一谈。

## 7. 验收

- 从工作台实际 MCP 链路返回原生游戏截图，AI 能在后台基于画面点击进入世界；图片比例、坐标和目标窗口正确。
- 在正常游戏中完成移动、转向、打开背包、取放物品、输入文字并重新观察，不依赖控制 Mod。
- 窗口移动、缩放、跨 DPI 屏幕、全屏/窗口切换以及游戏重建窗口后仍能恢复操作；鼠标捕获和原始输入设置纳入实测。
- 用户在前台编辑器连续输入时，后台游戏同时移动、转向和操作容器，文本与光标均不受 AI 影响；游戏失焦不自动暂停，也不反复抢前台。
- 普通遮挡、最小化、隐藏、锁屏分别记录输入和帧更新结果；没有新帧就不能通过对应运行状态的验收。
- 用户接管、停止、取消、桥异常和项目切换不会留下持续按键；过期坐标及会话被拒绝。
- 老版与现代版共用同一协议，不因 MC/Loader 不在第三方目录中拒绝看图和操作。
- 打包后的功能插件、实际工作台工具发现/调用、图片回读、只读限制和失败恢复均通过。
- 页面检查实际 1080×680 窗口与常用桌面尺寸、深浅主题和加载/失败状态；控制状态清楚，停止操作就近可达。
- 已有本地游戏和资源可用时验证断网控制；基础控制不额外下载游戏或逐版本测试组件。

第一步时的历史状态（2026-10-29）：当时已增加公共 Java Agent、LWJGL2/GLFW 两类虚拟输入、真实 framebuffer 捕获及受管会话服务，在原版 1.12.2/1.20.1 验证基础后台操作；当时全版本/Loader 验收和公开 MCP 接入尚未完成。后续完整交付见本文开头的最终记录，不以两个原版样本替代全部组合的验收。
