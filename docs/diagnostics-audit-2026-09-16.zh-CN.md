## 缺口、影响与修补建议

### P1：无法判定上一次是否正常结束

证据：`src/main/index.ts` 的启动、shutdownApplication、window-all-closed；`src/main/diagnosticLog.ts` 的 installProcessDiagnosticHandlers。

当前实现有 startup、shutdown/start 和 shutdown/timeout，缺少独立持久化的会话结束状态以及下一次启动时的对账。正常退出开始与退出完成也没有完整闭环。原生致命错误、系统强杀、断电和主进程 OOM 未必触发 JS 异常钩子。

建议：持有单实例锁后建立会话状态，低频更新心跳，在实际正常退出路径写结束标记；新启动核对旧会话状态并归类为“正常退出”“未确认正常结束”“已记录崩溃”。未确认结束不能直接计作崩溃；首次启用、多实例、更新重启、标记文件损坏也要分别处理。会话历史不应依赖普通日志是否已轮转。

### P1：嵌入式 Blockbench 的错误采集不完整

证据：`src/main/blockbenchBridge.ts:1065` 创建独立 WebContentsView，没有加载主界面的 preload；`:1797` 的 bindLifecycleEvents 只处理加载失败和 render-process-gone。主界面 error/unhandledrejection 监听位于 `src/preload/index.ts:40`。

因此不能依赖主窗口错误监听采集建模页面内部的 JS 异常、未处理 Promise、控制台错误和 WebGL context lost。直接在 Blockbench 内操作也未必经过 ModMind 的 IPC。已有渲染器退出监听只向状态消息写入 reason，缺少完整退出码、进程身份和当时操作上下文；没有独立的建模页面无响应诊断。

建议：为建模 WebContents 增加专用错误、控制台、响应状态和图形上下文事件采集；保留 reason、exitCode、webContentsId、OS PID、文档标识、最近操作。按签名限频，记录重复次数；清楚区分主动关闭与异常退出。

### P1：致命故障与性能异常缺少系统级证据

证据：应用源码没有启用 crashReporter、采集 app child-process-gone、定期 app.getAppMetrics 或事件循环延迟；内存数据只出现在导出时的 summary 中。导出没有采集 Electron crashDumps 路径。

“主窗口还在但模型黑屏”“GPU 进程退出”“主进程被内存压力终止”可能没有能定位的证据。JS uncaughtExceptionMonitor 无法替代原生崩溃转储。

建议：启用本地崩溃转储并纳入受大小限制的导出；采集 GPU/utility 子进程退出；低频记录主进程、主界面和建模渲染器的内存、CPU、主进程事件循环延迟，在异常时保留附近样本。原生转储可能包含敏感内存内容，应明确本地保存和导出策略；无需自动上传。

### P1：异步落盘可能丢尾部，日志自身的故障无法追溯

证据：`src/main/diagnosticLog.ts:263` 每条事件依次执行 mkdir/stat/append，写队列没有待写条数、字节数、最老事件年龄或背压上限。普通 error 和 renderer gone 事件使用异步 record。写失败只保留 lastWriteError，下一次成功会清空；flush 等待队列但不会告知调用者历史写入失败。

recordCritical 使用同步写入，与普通异步队列共同轮转同一组文件，没有共享的轮转互斥；存在交错竞争风险。这里是源码风险判断，本包不能证明竞争实际发生过。

此外 `src/main/index.ts:4321` 附近的独立 AI 日志写入以 catch(() => undefined) 吞掉失败。

建议：关键生命周期与致命事件使用独立、受限、同步的事件文件，避免与普通日志共享轮转；常规日志批量写入并限制待写字节；保留累计失败、丢弃数量、最后成功写入时间和队列延迟。诊断摘要必须能显示日志系统本身是否降级。

### P1：噪声日志挤占故障历史

证据：`src/main/diagnosticLog.ts:63` 默认只保留当前与上一份各约 8 MiB 的文件，内存只保留 2,000 条；`:270` 轮转删除更旧的文件。`src/main/index.ts:4313` 将 AI tool 正文同时写入普通事件日志，随后又写入独立 AI 输出文件。

本包仅几小时就消耗完一轮应用事件保留空间，早期会话已经缺头。即使扩大导出包，也无法找回已轮转删除的文件。

建议：普通事件只保留 AI 输出摘要、大小和关联 ID；正文放独立日志。错误/崩溃/会话生命周期使用独立配额，普通成功查询和频繁保存事件聚合或采样。保留期同时限制总大小与时间，并在导出摘要中显示实际起止时间、已轮转数量和已知缺口。

### P2：操作记录无法还原触发步骤，挂起调用没有超时证据

证据：`src/preload/index.ts:25` 的 invoke 只记录 channel、phase、duration；没有 requestId 和调用者窗口身份。`src/main/index.ts:7208` 的 blockbench:runAction 会将不同 action 映射成不同 command，但日志里只剩相同接口名。`src/main/blockbenchBridge.ts:1666` 直接等待 executeJavaScript；waitUntilReady 的单次 probe 同样没有独立超时。

多个相同接口同时运行时，无法可靠配对 start 与 success/error；渲染器在返回结果前退出时，客户端的完成日志也可能消失。建模脚本挂起可能长期只留下 start，后续串行任务也受阻。

建议：由主进程记录带 requestId 的操作闭环和 in-flight 状态；只采集允许列表内的动作名、文件类型/大小、模型数量、文档是否已保存等摘要，不记录完整参数或模型正文。建模桥接增加超时诊断和异常快照；超时本身不代表页面操作已取消，不能自动重试有副作用的动作。

### P2：页面快照无法展示建模现场，部分前端错误信息被丢弃

证据：`src/renderer/src/App.tsx:1938` 克隆的是主页面 documentElement，并存放在内存 Map；`:1983` 附近按路由等变化采样。Blockbench 是独立 WebContentsView，其 DOM 和 WebGL 画面不在外层 HTML 内。诊断包的 pages/blockbench.html 对应的 URL 也是 ModMind 主界面。

快照重启后不保留，不能复原退出前编辑器状态。AppErrorBoundary 把 componentStack 附加到 Error，但 preload rendererError 只传 name/message/stack，因此组件栈没有传入日志。

建议：导出明确注明每个快照的采集时间和所属 WebContents；建模额外采集有超时限制的状态摘要及可用截图。异常之前定期保存轻量上下文，不把重启后空白编辑器误作崩溃现场。错误上报显式传递 componentStack，并限制长度和敏感数据。

### P2：导出并非一致快照，核心日志可能受配额或截断影响

证据：`src/main/index.ts:3377` 只在导出开始 flush 一次，随后按顺序采集；应用日志直到 `:3512` 才采集。本包 summary 为 22:18:20.844，磁盘日志已到 22:18:31.533。success 事件发生在 ZIP 写完后，所以本次包内只有 export/start 是预期行为，不能据此判定导出失败。

`src/main/diagnosticArchive.ts:105` 先 stat 后 readFile，持续增长的文件可能突破预检查大小；大文本直接按字节取尾部，未对齐 UTF-8 和 JSONL 行边界，截断标记本身也不是 JSON。核心 app-logs 排在大量项目历史日志之后；其他更大的项目可能先耗尽总配额。本包没有发生总体配额挤占。

`:210` 仅对根目录读取失败登记错误，子目录读取失败会静默跳过；summarizeDiagnosticDirectory 也将部分读取失败转为空列表。因此 collection-report 的 errors=0 不等同于所有候选内容均读取成功。

建议：先固定并收集会话、关键事件、崩溃和当前操作，再采历史日志；按文件描述符和固定大小边界读取快照，JSONL 保留完整行，将截断元数据放在 manifest。记录采集开始/结束、每文件范围、所有跳过/失败子目录和完整性等级；保留导出耗时，避免把时间不同的快照当成同一时刻。

## 修补顺序与验收

1. 先补会话正常结束判定、关键事件独立落盘、Blockbench 错误与进程身份、GPU/原生崩溃证据。目标：能区分已记录崩溃与原因未知的异常中断。
2. 再补操作 requestId、建模动作摘要、内存/CPU/事件循环趋势和挂起诊断。目标：能知道出问题前在做什么，哪个进程先失去响应。
3. 调整日志分层、保留策略、导出顺序与完整性报告。目标：故障证据不被 AI 大量输出挤掉，缺失时能明确说出缺了什么。

建议使用隔离的临时用户目录验证：正常退出、更新重启、强杀主进程、仅结束建模渲染器、页面 JS 异常、WebGL context lost、并发相同 IPC、建模调用挂起、大量 AI 输出导致轮转、磁盘写入失败后恢复、导出时仍持续写日志。故障注入不得针对用户正在使用的项目或应用进程。

现有验证：`npx vitest run src/main/diagnosticLog.test.ts src/main/diagnosticArchive.test.ts`，2 个文件、6 个测试通过。现有测试覆盖脱敏、基本持久化、关键同步写入、采集与文本取尾；没有覆盖以上多数故障场景。通过现有测试不能证明崩溃诊断闭环完整。
